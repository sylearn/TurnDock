# 01 · 产品定义

## 目标与用户

面向同时使用多个本地 AI 编程客户端的人。AI 在需要确认、选择、补充材料时，通过 MCP 留下一条待回复请求；用户在自己的节奏内回答。产品的基本单位是「一次需要人回应的请求」，不是聊天消息、自动化流程或提示词模板。

成功体验：收到问题后快速辨认来源；长消息也能方便回答；离开数小时再回来，草稿和上下文仍然清楚；不同项目不串回复；没有回复时 AI 不被误导为获得许可。

## 核心能力继承与取舍

| 寸止能力 | TurnDock 决策 | 原因与阶段 |
|---|---|---|
| `zhi` 问题、Markdown、预设选项 | 保留兼容入口，新增明确选择类型 | 现有客户端能迁移；M1–M2 |
| 自由文本、图片粘贴 | 保留，类型与大小校验 | 原子提交，避免丢图；M3 |
| 主题、快捷键、通知 | 保留，尊重系统和输入法 | 不干扰用户当前工作；M2–M3 |
| 多客户端等待 | 统一请求列表、来源标签、独立草稿 | 新的首要能力；M1–M2 |
| 记忆工具 | 不纳入首版 | AI 记忆属于客户端/专用 MCP，避免重复数据责任 |
| ACE 代码搜索与源码上传 | 不纳入 | 与人机确认无关，且增加代码外传和索引成本 |
| Telegram 回复 | 后续可选独立适配器 | 必须绑定请求身份、单一消费者、去重与撤销；M5 另立方案 |
| 自动继续、隐藏增强提示词 | 不照搬 | 回复应是用户看得到的决定 |
| 应用内更新 | 必须做可信发布；可延后自动更新 | 签名、桥接器兼容、回滚比“有更新按钮”重要；M4 |

## 首版边界

必须有：请求列表与详情；安全 Markdown；单选/多选/自由回复；文本与图片；草稿保存；明确拒绝；取消/断线/过期状态；24 小时等待能力验证；连接诊断；最小历史；基础键盘与辅助功能；旁路安装迁移。

不做：账号系统、团队协作、云端同步、移动端、内建模型、自动决定、任务编排器、代码 IDE、全文知识库、多种富文本编辑器、无限插件市场。

本轮选择本地桌面产品，不添加后台 Web 服务和远程数据库。用户若以后需要手机回复，再单独设计远程身份和安全模型。

## 用户故事与完成条件

| 用户故事 | 完成条件 |
|---|---|
| 三个项目同时问我 | 三条可区分请求；切换不丢草稿；回复只能到对应连接 |
| 一小时后再处理 | 无重复催促；请求仍等待或明确显示调用方已断开 |
| 我想暂时放下 | 稍后处理不发任何结果，草稿保存，任务留在待办 |
| 我明确不允许执行 | 拒绝必须显式触发，调用方得到可解释的否定结果 |
| 发出时连接断了 | 不能显示已经完成；草稿与投递阶段可查，无自动跨会话重发 |
| 发送两张截图后删一张 | 删除所选 ID 的图片，另一张不变；真实 MIME 与字节一致 |
| 输入中文时按回车 | 只确认输入法候选，不误发回复 |

## 产品评价

用真实任务验收：找出来源是否清楚、决定是否易懂、回复是否不会误投、故障后是否能解释。观察任务完成时间与误操作，不能拿视觉截图或总功能数代替体验。

发布前做至少 5 个代表性使用场景的人工走查；不要把这当统计显著性研究。默认不采集遥测；测量使用本地开发日志和用户自愿提供的脱敏诊断。

默认策略：不抢焦点；不常驻置顶；不重复提醒；未配置通知时在窗口内显示请求数量。可选通知只影响提示，不改变请求生命周期。
