# 09 · 方案深度审查（第二轮）

日期：2026-10-20。对象：README 与 docs/01–08、design/prototype。结论：**方向可行，可以进入 M0；但需要先补 3 个根本缺口，否则产品核心场景不成立。** 本文是审查意见，尚未改动其他文档。

## 总评

| 维度 | 评价 |
|---|---|
| 安全与正确性 | 优秀。状态机、幂等提交、取消竞态、delivery_unknown、Markdown/CSP 边界都比上游严谨，且区分了实测与推断 |
| 技术选型 | 合理。Tauri 2 + Rust + Vue 3 无需更换；缺少具体库选择，M0 容易反复 |
| 产品定位 | **有偏差**。把寸止抽象成「请求收件箱」，丢掉了它最主要的用途：让 AI 的一个回合不结束 |
| 长等待 | **不成立**。24 小时等待依赖宿主工具调用不超时，但主流宿主默认值远低于此 |
| UX/视觉 | 克制、可用，但还是“做得好的后台模板”，高频场景缺少轻量入口 |
| 路线 | 很稳，但到 M4 才能日常替换寸止，缺少早期自用的里程碑 |

## P0 · 必须先解决

### 1. 宿主超时会直接击穿“长等待”

文档把“客户端可能更早超时”写成脚注，但这是核心约束。例如 Codex 的 `mcp_servers.<id>.tool_timeout_sec` **默认 60 秒**（官方文档）；原型首个示例请求来源就是 Codex。按现在的设计，用户离开 1 分钟后请求就会失败，`离开数小时再回来` 这个故事不成立。

建议：

- **M0 第一项改为「宿主超时矩阵」**：Claude Code、Codex、Cursor、Claude Desktop 及用户实际使用的宿主，逐个实测默认超时、可配置项、progress 通知能否重置超时、取消行为。结果直接写进 fixture。
- **让请求生命周期与单次工具调用解耦（可续等协议）**：
  - 请求由 broker 持有，不随工具调用超时而结束。
  - bridge 按宿主配置，在超时前（如 Codex 50s）返回结构化的 `outcome: "pending"` 和 `request_id`，并在内容里明确告诉 AI 用 `await_reply(request_id)` 继续等。
  - 用户的回复先落库，由下一次 `await_reply` 领取；领取写出后才进入 handed_off。这样同一会话里宿主超时、甚至 AI 中途被打断再继续，都不会丢回复。
  - 代价是 AI 会多轮调用，耗 token 或请求次数。单次等待要尽量贴近宿主上限，并在设置里显示每个宿主的实际轮询间隔。
- 状态机相应增加“请求未结束、但当前没有工具调用挂着（detached）”的状态；`disconnected` 只表示 bridge 进程结束。
- 安装和迁移向导为能配置的宿主生成更长的超时配置（如 Codex 的 `tool_timeout_sec`），并解释原因。
- MCP tasks 是这件事的标准做法：宿主协商支持后优先使用，可续等协议作为兼容回退。

### 2. 找回寸止的真正核心：「回合不结束」

上游 README 的第一卖点是“AI 想结束时弹出继续选项”。实际使用中，大部分调用是**每轮工作结束时的检查点**，最常见的回复是“继续”或“接下来做 X”。在按请求计费的宿主里，这还意味着一次请求内能完成多轮协作。现方案只把它当“偶尔需要确认”的收件箱，会让老用户觉得变难用了。

建议：

- 01-产品定义把场景分为两类：**A 回合检查点（高频、短回复）** 和 **B 决策请求（低频、需要上下文）**，A 必须是最快路径。
- 保留“继续”，但要可见、可编辑：用户自己维护的快捷回复（如“继续”“按最佳实践继续”“先停下总结”），发出的内容就是用户看到的文字。不要隐藏增强提示词，也不要把这个能力删掉。
- **补上集成层，目前文档里完全没有**：
  - 寸止能不能用，取决于 AI 是否被要求“结束前必须调用”。需要交付：MCP server `instructions` 字段、高质量的工具 description，以及可复制的规则片段（CLAUDE.md / AGENTS.md / Cursor rules），并按宿主分别测试遵从率。
  - 在 Claude Code 上，可用 Stop hook 在 AI 想停止时确定性地拦截，不依赖模型是否遵守规则。作为可选适配器评估，比单纯靠提示词可靠。

### 3. 定位要回应 MCP elicitation 与宿主原生提问

MCP 已有 elicitation，Claude Code 也有原生提问工具，文档没有提到。需要一段明确的差异说明：跨宿主统一队列、可离开的长等待、图片回复、草稿与历史、不依赖各宿主的 UI 质量。否则无法回答“为什么不直接用宿主自带的”。

## P1 · UX 与视觉（离“顶级”还差什么）

**4. 缺少高频场景的轻量入口。** 目前只有 1120×780 的收件箱主窗口。高频的回合检查点应该分三层：

```text
系统通知 ──点击──▶ 快速回复面板（全局快捷键 / 菜单栏，约 560×420）──展开──▶ 完整收件箱
```

快速面板：只显示当前最早一条请求，数字键 1–9 选择选项，直接输入文字，⌘↵ 发送，Esc 收起但不取消，Tab 切到下一条。“不抢焦点”作为默认值是对的，但寸止用户习惯弹窗，应允许按宿主或项目设置“弹出 / 仅通知 / 静默”。macOS 通知内直接文本回复需要先验证 Tauri 插件是否支持，否则写入 M5。

**5. 完整的键盘模型**（目前只定义了 Tab 顺序）：J/K 或 ↑↓ 切换请求，1–9 选择选项，/ 搜索，⌘↵ 发送，⌘L 稍后处理，拒绝必须经过确认，⌘K 命令面板可选。所有快捷键都要先判断 IME 合成状态。

**6. 截图中的具体问题：**
- 正文出现前要经过 64px 品牌栏、67px 上下文栏，再加原生标题栏，接近 200px 的框架。建议用 macOS overlay titlebar，把来源/项目/连接状态合并成一条工具栏，窗口里不再放品牌名。
- 侧栏每条 116px 高，一屏只能放 3–5 条，削弱了多项目队列的意义。建议压到 64–72px：两行内容，来源用小标识，等待时长右对齐。
- 标题和正文限宽 70ch，但选项卡片和输入框占满 1060px，阅读区左对齐但宽度不一致。整列应该共用一个宽度（约 720px）。
- 列表里“已断开”用了强调蓝，与 02 文档的警示琥珀色不一致（原型 bug），而且看起来像可点击的链接。
- 侧栏的“你的决定，按你的节奏”以及“收件箱”大标题占用空间，但不提供信息。

**7. 色彩：** `#4159C6` 靛蓝配冷灰是 SaaS 产品最常见的组合，辨识度低。建议：
- 中性底色改为略带暖意的纸色/石墨色，强调色只用于“需要你行动”这一种语义。
- 给每个宿主分配可识别的来源标识（形状 + 颜色 + 名称，不只靠颜色）。在多项目场景下，这比品牌色更能提升识别速度。
- M2 用真实长消息做 2–3 个视觉方向的对照，再定 token，不要现在就锁定 6 个色值。
- 动效只用在三处：新请求进入、发送状态变化、面板展开；其他保持静止。

## P1 · 技术细化

**8. Markdown 在 Rust 侧渲染并净化**（pulldown-cmark 或 comrak + ammonia），前端只接收白名单 HTML。好处是只有一个安全边界，也去掉了上游 353KB gzip 的 Markdown 块；代码高亮在前端按语言懒加载。

**9. M0 前先定具体库，避免反复：**

| 用途 | 建议 |
|---|---|
| MCP | 官方 Rust SDK `rmcp`，锁定精确版本 |
| Rust→TS 类型 | `tauri-specta` 或 `ts-rs`，CI 检查生成物是否最新 |
| SQLite | `rusqlite` + 专用写线程 + `refinery` 迁移（同步单写入口比 sqlx 简单） |
| 无样式组件 | Reka UI（Vue headless），只用于对话框、菜单、Popover |
| 前端状态 | Pinia 只存视图状态；业务状态来自 Rust 快照 + revision |

**10. bridge 启动失败必须快速返回明确错误。** 应用未安装或启动失败时，在几秒内返回可读的错误，不要一直挂到宿主超时。macOS 用 bundle ID 启动（LaunchServices），不依赖路径。

## P2 · 路线调整

**11. 增加「M1.5 自用替换」里程碑。** 目前要到 M4 才能日常替换寸止。建议在 M1 之后，只针对用户最常用的一个宿主，交付以下内容：zhi 兼容、可续等、快速面板、快捷回复、规则片段。与寸止并行配置，作者自己每天使用两周，用真实数据修正后面的设计。delivery_unknown 等严谨状态照常实现，但视觉打磨放到 M2。

**12. 文案语气。** 规范里大量“不…不能…禁止”适合工程约束，但界面文案应以“你能做什么”为主。例如断线时，把“回复尚未送达”放在主要位置，“复制草稿”作为主按钮。
